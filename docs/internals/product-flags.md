# Product flags

UpComputer ships on upstream core but does not ship every upstream feature. It hides them instead of deleting them, so an upstream sync only has to keep a few hook lines instead of re-deleting rewritten files.

`packages/shared/src/productFlags.ts` is the one place that says what a product shows:

- `ProductFlags` lists the hideable features: `pullRequests`, `terminalSurface`, `terminal`, `threadSettlement`, `devices`, `mcpOAuth`, `scheduledTaskWebhooks`, `defaultBrowser`, `cliCommand`, `mcpApps`, `usageDataNotice`, `t3Chat`, `triage`. The terminal is split in two: `terminalSurface` is the terminal as a right-panel surface (its launcher entry and `+` menu item, its tab, the `terminal.*` shortcuts that only act while a terminal has focus, and the terminal font setting); `terminal` is everything else (the bottom drawer and its `terminal.toggle` shortcut, project scripts and `script.*`, "Run in terminal", the worktree setup terminal, the running-terminal badge on thread rows).
- `UPSTREAM_PRODUCT_FLAGS` shows everything. Core without a product composition uses it, so stock core and upstream's own tests behave as upstream.
- `UPCOMPUTER_PRODUCT_FLAGS` shows `terminalSurface`, `mcpOAuth`, `scheduledTaskWebhooks`, `defaultBrowser`, `cliCommand`, `mcpApps` and `usageDataNotice` and hides every other flag. The public build (`apps/server/src/product/publicProduct.ts`, `apps/web/src/product/productEntry.ts`) and pro pass it to `composeExperimentalServerFeatures` / `composeExperimentalWebFeatures`.
- A table in the same module maps each flag to the capabilities, keybinding commands, settings search items and right-panel launchers it hides.

## Server hooks

The composition carries the flags; upstream files read them through `ServerProduct`:

- `environment/ServerEnvironment.ts`: the descriptor drops the pull request and settlement capabilities. Every client, web and mobile, already hides that UI when a capability is missing.
- `server.ts`: the settlement worker and the pull request workers (branch PR sync, linked PR sync, PR watch) do not start. `whenProductFeature` drops a layer; `isProductFeatureShown` guards a start effect whose service other layers still need.
- `mcp/McpHttpServer.ts`: agents do not get the pull request and device tools, review guide tools included.
- `pullRequest/PullRequestReviewGuideService.ts`: `generate` refuses without `pullRequests`, so no client can start a review guide's model run.
- `server.ts`, `mcpOAuth`: outside agents cannot sign in to `/mcp`. The OAuth endpoints answer 404 (`whenProductFeatureOr` with the stand-ins in `product/hiddenHttpGroups.ts`, since the HTTP API keeps the group), and `/mcp` gets no `McpClientAuthenticator`, so it accepts only provider-session tokens and advertises no OAuth metadata.
- `server.ts`, `scheduledTaskWebhooks`: the hook route answers 404 the same way, and `scheduledTasks/ScheduledTaskService.ts` refuses to save a webhook schedule, so an agent's `schedule_task` cannot create one.

`defaultBrowser` is read at build time: `scripts/build-desktop-artifact.ts` registers the macOS `http`/`https` protocols and web page document types only when `UPCOMPUTER_PRODUCT_FLAGS.defaultBrowser` is on; without them macOS never lists the app as a default browser. Local Test builds register them too (only the app's own schemes are left out there), so a Local Test install also appears in the list.

The terminal and device services stay: worktree setup scripts run in a server terminal, and the device service idles unless device support is turned on in settings, which the product hides.

## Web hooks

The web composition carries the flags too. Upstream files call `apps/web/src/product/productFlags.ts`, which reads them lazily because upstream state modules import it:

- The resolved keybindings (`state/server.ts`, the Keybindings settings page) drop the drawer toggle, project script, pull request and settle commands, so their shortcuts, labels and rows go with them. Without `terminalSurface` every `terminal.*` command goes.
- Settings search filters the hidden rows; the rows themselves are gated where they render (terminal font and its preview, behind `terminalSurface`; device settings, PR merge method and agent credit removal, GitHub routing, review guides).
- The right-panel launchers drop the Pull request, Linked pull requests and Device entries, and the Terminal entry without `terminalSurface`.
- Chat view: no terminal drawer toggle, project scripts, "Run in terminal" or setup-terminal button, and no device state subscription. Without `terminal` the drawer never renders, and `terminal.new`, `terminal.split*` and `terminal.close` act on the right-panel terminal (`terminalCommandTarget`), since a custom shortcut can drop the default's `terminalFocus` condition.
- No PR badges or PR summary reads (`useLinkedThreadPullRequest`), no `#` pull request menu in the composer, no Pull requests entry in the sidebar footer, the compact sidebar (`usePullRequestsSupported`) or the command palette, pull request links open as ordinary links, not in the app (`openPullRequestLink.ts`), and `/pull-requests` redirects home.
- The sidebar has no Settled section and no bulk Settle.
- Thread search (sidebar and command palette) does not match pull request numbers, and the matched PR number is not shown (`Sidebar.logic.ts`, `CommandPalette.logic.ts`, `ThreadSearchPullRequestNumber`).
- `mcpOAuth`: `/connect-agent` redirects home.
- `scheduledTaskWebhooks`: Scheduled prompts offer no "On webhook" trigger (an existing webhook task keeps its own), and Connections hides "Hold webhooks while offline".
- `cliCommand`: no `up` command row in Settings, General.
- `mcpApps`: MCP app results show as ordinary tool calls instead of inline apps (`session-logic.ts`).
- `usageDataNotice`: onboarding shows no note on usage data and Settings no privacy policy row. Both link `PRIVACY_POLICY_URL` in `apps/web/src/legalLinks.ts`, which points at Up.computer's policy, so their copy describes Up.computer's telemetry rather than upstream's.
- `t3Chat`: no T3 Chat page in the UpComputer Connect account menu and no T3 Chat upgrade links under the tunnel meter. Our relay has no T3 Chat link secret, so the link is off there anyway.
- `triage`: no "Triage an issue" in the command palette. Its playbook files issues against upstream's repository, so the server's `triage` capability is off.
- Terminal metadata (`state/terminalSessions.ts`): `useKnownTerminalSessions` subscribes with `terminalSurface`, since the panel tab takes its labels and working directories from it and ChatView allocates terminal ids from it; `useThreadRunningTerminalIds`, the thread rows' running-terminal badge, needs `terminal` too.

Web unit tests alias `product/productEntry` to `apps/web/test/coreProductEntry.ts`, so upstream's tests run with upstream's flags. Tests for a hidden feature mock the entry, as `product/productFlags.test.tsx` does.

## Surfaces

Some upstream UI is replaced rather than hidden. `ProductSurfaces` in the same module names each replaceable surface, and its value is `upstream` (exactly upstream's UI) or `upcomputer` (the product's version). `UPSTREAM_PRODUCT_SURFACES` is core's default; the public build passes `UPCOMPUTER_PRODUCT_SURFACES` to the web composition. The product's version lives in its own files, and upstream's file gets a minimal hook through `productSurface` in `apps/web/src/product/productFlags.ts`:

- `sidebarProjects`: the sidebar's Projects and Threads sections (`apps/web/src/sidebarProjects/`) under the navigation entries, and a search row with search only, at the rows' regular weight (`components/sidebar/SidebarThreadHeader.tsx`): Add project and New thread move into the section headers. The Projects section reads and writes upstream's persisted project scope, so the thread list filters exactly as upstream's scope menu does. The Threads header only collapses upstream's thread list (`useSidebarThreadListShown` in `Sidebar.tsx`); the list itself is upstream's. New thread, both the Threads pencil and `chat.new` (gated in `routes/_chat.tsx`), starts a thread without a project through upstream's scratch project, as V1 did; Shift+click on the pencil runs upstream's click (the project picker), and the command palette labels its "New thread in <project>" item with `chat.newLocal` instead.
- `sidebarThreadRow`: the sidebar's thread rows. Here the product's version is also a user choice: Settings, Appearance, "Thread list" (the `sidebarThreadList` client setting, stored like Chat width) picks the compact one-line row (`apps/web/src/sidebarThreadRow/`, the default) or upstream's detailed row, and the sidebar switches at once. `Sidebar.tsx` swaps the row component it renders, so both rows get the same props from upstream's list, shelves and actions. Both rows show a thread's status as V1's text label (`ThreadStatusLabel`): upstream's status derivation decides the kind, and in upstream's detailed row the label replaces only its status indicator. With `upstream` the setting row and its settings search entry are hidden and the rows are upstream's.
- `sidebarHeader`: the sidebar's titlebar row (`components/sidebar/SidebarChrome.tsx`) shows no brand and no stage badge, and `AppSidebarLayout.tsx` moves the sidebar toggle so its icon starts where the row icons do (`SIDEBAR_TOGGLE_ALIGNMENT` in `apps/web/src/sidebarMetrics/`). With `sidebarLayout` the toggle shows only on phones. The stage label stays everywhere else, and the header keeps its titlebar height and drag region.
- `composerFooter`: the composer's footer row in V1's layout (`apps/web/src/composerFooter/`), built from upstream's own controls: attach, Build or Plan, provider and model in one label, effort and context in upstream's traits picker, access as a lock with upstream's access menu, then the context ring and send. Trailing controls fold into upstream's `CompactComposerControlsMenu` as V1's footer did. `ChatComposer.tsx` hands the row upstream's file input, model picker and primary actions as elements (`composerAttachmentInput`, `composerModelPicker`, `composerPrimaryActions`), renders the picker through `ComposerFooterModelPicker` for the combined label, and takes the idle placeholder from `composerIdlePlaceholder`. The look is V1's too (`composerLookStyles.ts`): text-only controls with no chevrons, V1's card, padding and placeholder tone (`composerLookClass` hooks on `ComposerSurface.Shell` in `ChatView.tsx` and on the surface, prompt body and editor in `ChatComposer.tsx`), V1's grey send button in `ComposerPrimaryActions.tsx`, and V1's opaque fade behind the docked composer (`ComposerBackdropFade`). Its colors, and the row's under it, are only the `--composer-*` tokens in `theme.upcomputer.css`: V1's values in the Up.computer theme, derived from the theme's own tokens in every other, so a class with a color literal would ignore the theme. While focus is outside it and its menus, the composer compacts to one row of paperclip, prompt and send (`compactComposer.ts`, the "Compact composer" setting). It only restyles the same card, so the prompt editor is never remounted, and it reports itself to `ChatView.tsx` as resting so the timeline keeps reserving the full composer's height and expanding never covers the last message. The stash badge, queued runs, usage limits, banners and the mobile collapsed composer stay upstream's.
- `composerContextRow`: V1's row under the composer card (`apps/web/src/composerContextRow/`) replaces upstream's context strip with upstream's environment, checkout mode and branch selectors shown as text; with none of them to show (`contextRowControls.ts`), the row and its space under the composer are left out. `ChatView.tsx` turns off upstream's strip (`hasActiveProject`) and renders the row under `ComposerSurface.Shell` with the same props it gives `BranchToolbar` (and `branchToolbarRef`, so the branch and previous-worktree shortcuts reach it). `ChatComposer.tsx` looks for control shortcut triggers in the whole composer stack (`composerShortcutScope`), and the row hides the branch selector's pull request badge (`showPullRequestBadge`). The resting composer's controls fall back to upstream's model strip. The panel toggles stay upstream's, in the header. In place of upstream's project breadcrumb, `ChatHeader.tsx` shows the chat's projects (`ThreadHeaderProjects`): one project's icon and name, several projects' icons only, or a dashed square for a chat without a project. It opens a searchable list that links and unlinks projects; an unsent chat without a project moves into the chosen one, and an unsent chat in a project links more after its first message. The linked-projects header accessory renders nothing. The empty draft's project picker keeps V1's "No project" item first, which upstream moved to the line under the heading (`showsDraftHeroNoProjectItem`).
- `sidebarVibrancy`: V1's translucent sidebar on the macOS desktop app. The desktop creates its darwin main window transparent over the native `sidebar` vibrancy (`apps/desktop/src/window/UpcomputerWindowVibrancy.ts`, applied in `DesktopWindow.ts` on creation and on appearance changes). The main process cannot know the theme, and a transparent window cannot turn opaque later, so the page decides: `main.tsx` marks the document (`apps/web/src/sidebarVibrancy/`), and `theme.upcomputer.css` makes html and body transparent and paints the sidebar with V1's translucent tints, row tones and borders only with the Up.computer theme and only while the app sidebar is mounted. Text legibility leans on the native material, as in V1; there is no contrast floor over an arbitrary backdrop. V1's `backdrop-filter` is kept for parity, but it cannot sample the native layer, so it changes nothing visible. Any other theme, a browser, or another platform paints the page opaque. Nothing in the translucent sidebar animates, except drag and drop. A hidden browser guest that keeps rendering for an agent, a recording or picture in picture waits behind the opaque chat inset instead of upstream's window origin, which would show the page through the sidebar (`apps/web/src/sidebarVibrancy/hiddenBrowserBackdrop.ts`).
- `sidebarNotifications`: one bell in the sidebar footer (`apps/web/src/sidebarNotifications/`) replaces upstream's update control and holds the background notices too. Its dot takes the most important item's colour (error, warning, else neutral); the popover has Updates on top and Notifications below. The update actions are upstream's (`useDesktopUpdateState`, `useUpdateEverything`, the exported `downloadLocalUpdate` and `installLocalUpdate` in `SidebarUpdatePill.tsx`). While Update everything runs, the bell renders upstream's `SidebarUpdatePill` beside it, which shows only its progress capsule then. With `upstream` the footer shows upstream's control and no background notices.

- `sidebarLayout`: one desktop sidebar whose width decides its mode (`apps/web/src/adaptiveSidebar/`). There is no hide button: `AppSidebarLayout.tsx` hides upstream's toggle on desktop and does not mount upstream's `CompactSidebar`. Dragged below `SIDEBAR_COMPACT_THRESHOLD` the sidebar snaps to a column of the same rows as icons, and dragged back out it returns at its previous width; `sidebar.toggle` switches the two. The resize rail takes a `dragWidth` hook (`components/ui/sidebar.tsx`) that maps each dragged width and sets `data-sidebar-compact` on the wrapper while the drag crosses the threshold, so nothing renders mid-drag; `adaptiveSidebar.css` draws the column from that attribute: a row's first child centred, a dot for its end labels, open section headers as dividers, collapsed sections and the footer's notices left out. The full width stays in upstream's width key, the mode in `upcomputer:sidebar-compact`. Rows get their names as tooltips through `SidebarCompactTooltip`, the search row becomes a command palette button (`SidebarCompactSearch` in `SidebarThreadHeader.tsx`), and the page titles clear the macOS window controls beside the column (`workspaceTitlebar.ts`). Phones keep upstream's sheet. A navigation contribution with `placement: "footer"` (the Agents page) is an icon button after Settings in the footer instead of a row.
- `threadDetailsCard`: the thread details card (upstream's `ThreadDetailsCard` on the chat canvas) is closed in every thread until the user opens it with its header toggle or `threadPanel.toggle`. `rightPanelStore.ts` takes its default visibility from `apps/web/src/threadDetailsCard/`, so it persists the threads where the card is open instead of the ones where it is closed (an old closed entry equals the default and is dropped), and closing the right panel over an open popover no longer opens the inline card. Inline or popover placement stays upstream's.

## Mobile app

The mobile app is not a flag: `pnpm-workspace.yaml` excludes `apps/mobile` from install and build, and `allowUnusedPatches` keeps its patch entries valid. Upstream's mobile CI workflows filter on `@t3tools/mobile` and would fail; this fork does not run them.

## Sync rule

Every hook goes through `productFlags`, `whenProductFeature` or `isProductFeatureShown`. After an upstream sync, `git grep -n -e productFlags -e whenProductFeature -e isProductFeatureShown -e productSurface` lists the hooks to re-check. When upstream adds a new entry point to a hidden feature, gate it the same way.
